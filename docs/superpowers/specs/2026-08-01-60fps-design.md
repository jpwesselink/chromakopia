# Design: 60fps renderer + tempo normalization + single render loop

**Date:** 2026-08-01
**Status:** Approved

## Problem

`FPS` is 30 (docs falsely say 60). At 30fps, a 60 cells/s marquee strides
2 cells per frame and judders on big glyphs. Separately, the animate/render
task pair share a mailbox with burst catch-up — under load the animation
can outrun the renderer and the scroll teleports.

## Changes

### 1. `FPS = 60.0`

`src/animate/framebuffer.rs:17`. Everything seconds-based
(`secs_to_frames`, durations, Timeline/Phases windows, cue math,
`Marquee`/`Wind` which already use `frame / FPS`) adjusts automatically.

### 2. `tempo()` — legacy speed units stay valid

New in `framebuffer.rs`:

```rust
/// Frame count in "tempo units" — one unit = one frame at the original
/// 30fps tuning. Phase-accumulating effects multiply their speed knobs
/// by this instead of the raw frame count, so tuned constants keep the
/// same on-screen speed at any FPS.
pub fn tempo(frame: usize) -> f64 { frame as f64 * 30.0 / FPS }
```

Every phase-accumulator site in `effects.rs` switches `frame as f64` →
`tempo(frame)`: Glow spotlight, Glitch `t`, VectorField `t`, HeightMap
`t`, Radar sweep, Neon pulse, VSineWave `t`, Dycp `t` + scroll offset,
Fld `t` + palette shift `(x + frame)`, Pulse's `frame % 120` cycle and
Karaoke's `frame % (total + 20)` reveal (integer cadences become
`tempo(frame) as usize`). Duration-normalized sites
(`frame / total_frames`) are already FPS-safe and stay untouched.
`tempo` is exported alongside `secs_to_frames` for examples.

### 3. Single render loop, jitter-proof ticks

In both `run_effect` and `spawn_effect`: merge the animation task and
render task into one task — tick → render effect → diff → write. The
`Mailbox` type and its `Arc<Mutex<Option<FrameBuffer>>>` handoff are
deleted; frame production and display are 1:1 by construction.
`interval.set_missed_tick_behavior(MissedTickBehavior::Skip)` so a
stalled tick slows the animation for a beat instead of teleporting it.
Frame period becomes `Duration::from_secs_f64(1.0 / FPS / speed)` (the
old integer-ms truncation ran 31fps instead of 30). The fps counter and
command handling (fade/transition/stop) keep working unchanged.

### 4. Examples sweep

`frame as f64 * <speed>` phase math in custom example effects switches
to `tempo(frame)`: `cube_rotate` (oscillator), `dotsec_logo`,
`letters_drop`, `letters_parallax`, `timeline_demo`, `greetings`
(NamesSequence wobble). Seconds-based example code is untouched.

### 5. Tests + docs

- The three `vsinewave` envelope/displacement tests re-derive their
  frame numbers under `tempo` (frames double: 1→2, 33→66; the
  `FrameProbe` continuity test is unaffected — it checks raw frame
  passthrough).
- Fix the stale `run_effect` doc ("60fps" is now true); update any other
  "30fps" comments found in the sweep.
- After landing: update the `fast-cli-animations` memory note (strobe
  ceiling doubles to ~90 cells/s at 60fps).

## Acceptance

- Full test suite passes.
- `cargo check --examples` clean.
- Pty run of `greetings`: fps counter reads ~60, steady.
- Visual parity: all effect speeds look the same as before (tempo
  guarantees it analytically; spot-check marquee + greetings by eye).

## Out of scope

- Changing any public speed-knob units (tempo keeps 30fps-era units).
- Configurable FPS.
